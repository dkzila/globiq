## What Was Delivered

### 1. Data Model (`prisma/schema.prisma`)

- `User` extended (§6): `passwordHash` (nullable — reserved for future non-password auth), `role` (`READER | WRITER | COUNTRY_ADMIN | ADMIN`), `status` (`ACTIVE | SUSPENDED | DELETED`), `authMethod` (`PASSWORD`), `emailVerifiedAt`, `lastLoginAt`.
- New `AuthSession` model: one row per issued Bearer token — stores only the **SHA-256 hash** of the token, a device label, `lastUsedAt`, `expiresAt` (30 days), `revokedAt`.
- Onboarding state intentionally deferred to P5-S3 (session protocol §41 — never early).

### 2. Identity & Access Module (`src/modules/identity-access/`)

First full module per the §28 modular-monolith rules, exposing an explicit public interface:

- `password.ts` — scrypt hashing via Node `node:crypto` (OWASP parameters, constant-time verify, zero crypto dependencies).
- `token.ts` — 256-bit opaque tokens (`globiq_…`), SHA-256 hashing, 30-day expiry.
- `validation.ts` — zod schemas for register/login with explicit field errors.
- `service.ts` — domain logic: register (server-side country/language resolution per §14/§35), login (uniform `INVALID_CREDENTIALS` — no user enumeration), request authentication, session listing/revocation, `lastUsedAt` throttled touch (≤1 write/min).
- Why opaque tokens, not JWTs: server-side revocation is a §30 requirement (logout, device revocation) — impossible with stateless JWTs.

### 3. APIs (§37: domain-oriented, client-agnostic, explicit errors)

| Endpoint | Method | Auth | Purpose |
|---|---|---|---|
| `/api/auth/register` | POST | — | Create account → user + token grant (201) |
| `/api/auth/login` | POST | — | Email + password → user + token grant |
| `/api/auth/logout` | POST | Bearer | Revoke current session |
| `/api/auth/me` | GET | Bearer | Current user + session |
| `/api/auth/sessions` | GET | Bearer | List active sessions (current marked) |
| `/api/auth/sessions/[id]` | DELETE | Bearer | Revoke one session (own only) |

- Error contract extended: `UNAUTHORIZED` (401), `FORBIDDEN` (403), `CONFLICT` (409, e.g. `EMAIL_TAKEN`), `RATE_LIMITED` (429 with `retryAfterSec`).
- Rate limiting (§30): in-memory sliding window per IP — register 5/hour, login 10/15min; signature designed to swap to a shared store at scale (§29).
- `/api` index updated with the auth surface.

### 4. Web (temporary foundation page, `/` only)

- **Account section** (`src/components/auth/account-section.tsx`): sign-in/create-account tabs (react-hook-form + zod), profile card (role, home country, preferred language, member since), sessions manager (device icons, "This device" badge, revocation with confirm dialog, slim scrollbars).
- **Header auth area**: signed-in chip + sign out, or "Sign in" anchor.
- **Client state** (`src/stores/auth.ts`): Zustand + persist — only the token is persisted; user/session always re-verified via `/api/auth/me` (client never trusts its cache for identity). 401s anywhere clear the session.
- The site consumes the same endpoints a future app would (§4) — no private shortcuts.

### 5. Seed (§45)

- Dev-only admin: `admin@globiq.dev` / `GlobIQ-Dev-Admin-1` (role `ADMIN`, India/English, email-marked-verified). Upsert never overwrites a changed password. Full scoped staff seeding arrives with the editorial console (P2-S4/S5).
