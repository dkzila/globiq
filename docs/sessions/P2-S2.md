## What Was Delivered

### 1. Schema (Prisma → Supabase)

- `ContentFormat` — 7 §23 representation formats: FACT_CARD, EXPLAINER, REVISION_NOTE, CURRENT_EVENT_UPDATE, TIMELINE, PROFILE, COMPARISON. (QnA/Question/MockTest are separate entities in P7 — never ContentItem formats; canonical semantic types already live on KnowledgeUnit.)
- `ContentStatus` — DRAFT → IN_REVIEW → PUBLISHED → RETIRED (withdraw/archive, §19 step 10). SCHEDULED joins in P2-S4 with the editorial workspace.
- `ContentItem` — `knowledgeUnitId` + `languageId` + `format` (`@@unique` — §7/§11 identity rule applied to representations: one rendering per unit×language×format); `title`/`body` = **working copy** (editorial staging); `publishedRevisionId` = live-revision pointer; `createdById` → SetNull.
- `ContentRevision` — immutable published snapshot: `revisionNumber` (unique per item), `title`, `body`, `changeSummary` (§25/§36 provenance), `publishedById`/`publishedAt`. Rows are never updated or deleted — publishing appends N+1 and moves the pointer (transaction + unique guard against concurrent double-publish).

### 2. Revision Semantics (§19/§36)

- **Working copy vs live revision**: public reads ALWAYS serve the live `ContentRevision` — staged corrections on a PUBLISHED item are invisible until a new revision is published (verified end-to-end).
- **Correction cycle**: edit working copy → publish → revision N+1 with a **required** changeSummary (CHANGE_SUMMARY_REQUIRED) and a NO_CHANGES guard against identical re-publishes.
- **State machine** `CONTENT_TRANSITIONS`/`CONTENT_EDITABILITY` exported as the single source for service + UI: DRAFT→submit_review→IN_REVIEW→publish→PUBLISHED; PUBLISHED→publish (new revision, same status); any live status→retire→RETIRED (read-only end-of-life).
- **Publish preconditions**: owning unit must be VERIFIED (UNIT_NOT_VERIFIED — a representation is never more visible than its canonical record); working copy re-validated against §23 format rules at publish time.

## Key Decisions

1. **Working copy on ContentItem + immutable ContentRevision rows** — the classic editorial pattern that satisfies §19/§36 exactly: public reads serve the live snapshot; corrections stage invisibly and publish a new revision. No revision table migration needed later — it IS the P2-S1 handoff's promised upgrade from audit-diff interim history.
2. **Identity = unit × language × format, immutable post-create** (§7/§11 applied to representations) — enforced by a compound unique; even RETIRED items block identity reuse (§36 migration-safe philosophy).
3. **Country scope inherited from the owning unit** — a representation has no independent country field; COUNTRY_ADMIN parity with taxonomy/KU rules (global = read-only, own-country = manageable).
4. **§35 enforced server-side on create AND read** — country-scoped units accept only languages configured for their market; public lists expose only the resolved country's configured languages (the FR view proves English content is invisible where English isn't configured).
5. **Publish requires a VERIFIED unit** — the representation-never-more-visible-than-its-record rule, layered on top of topic-visibility delegation.
6. **changeSummary required on re-publish, NO_CHANGES guard** — corrections are never silent (§25/§36) and revision spam is impossible.
7. **SCHEDULED deferred to P2-S4** per the P2-S1 handoff — the state-machine map is the shared vocabulary to extend.
8. **content:manage as its own permission** — P2-S4 only needs to add the WRITER grant (§18 "Writer: create/edit assigned content").
