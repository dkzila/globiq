## What Was Delivered

### 1. The engine (`src/modules/exam-mapping/combination-service.ts` — new file in the §28 registry's exam-mapping module)

`getCombinedExamView(query)` implements §11 step by step (numbered in code comments):

1. **Collect the exam set** — refs (slugs or ids) deduplicated case-insensitively AND by resolved exam id (slug + id of the same exam collapse; the union is over exams, not strings). Until P5-S1 wires follows, the client passes the set explicitly; single-exam mode is one ref.
2. **Resolve each exam to its ACTIVE ExamVersion** — the §36 window containing now (future versions never contribute). An ACTIVE exam with no current version resolves gracefully (`version: null` + note + zero contribution) instead of failing the request. Unknown/non-ACTIVE/out-of-country refs are uniform `EXAM_NOT_FOUND` 404s (no enumeration).
3. **Expand** each version's nodes + mappings in parallel; public reality mirrors `getPublicExamCoverage`: VERIFIED units, country-visible (GLOBAL or the exam's country), currently in effect (§8 period; future-effective mappings excluded).
4. **Union by canonical unit id** — a `Map<unitId, accumulator>`; one covering row per (exam × node) so a unit anchored at several nodes of one exam keeps each requirement.
5. **Shared units keep the MAXIMUM requiredDepth** (ONE_LINE < FACT < CONCEPT < DETAILED < ANALYTICAL) plus the distinct covering-exam set (request order — the badge input) and per-covering depths (the ladder stays visible). Strongest priority/likelihood surface for ranking; `latestEffectiveFrom` as the freshness signal.
6. **Dedup strictly by canonical identity** — never by title/text similarity.
7. **Base ranking** (§11 step 7): priority → question likelihood → freshness (newest `effectiveFrom` first, never-attached last) → canonicalName → slug — plain code-unit comparisons, fully deterministic (§37). The comparator is documented as the single merge point for P5 personalisation and P7 mastery/revision signals (they fold in as earlier comparators; the union/dedup/depth rules never change).
8. **Every item rendered once** with its covering set — the API ships the data; the UI says "Covers: …".

Nothing persists: no writes, no audit, no storage — `computedAt` records the request time (§46.3).

## Key Decisions

1. **The engine lives in the exam-mapping module** (per the §28 registry: "multi-exam union & deduplication engine", P3-S3…S5) as a sibling service importing the module's shared internals — no new module, no schema, no seed.
2. **An exam set, not a string list**: refs dedupe case-insensitively AND by resolved exam id — "upsc-civil-services" + its cuid are one exam. The response's `exams` array carries each exam once, in request order.
3. **Graceful versionlessness**: an ACTIVE exam with no current version resolves with `version: null` + a note and contributes nothing — the request still succeeds (a followed-but-not-yet-published exam must not break a learner's queue). Unknown/invisible refs still 404 the whole request (§37 actionable: the message echoes the offending ref).
4. **Base ranking with a documented merge point**: priority → likelihood → freshness → name → slug, deterministic; P5 personalisation and P7 mastery/revision fold in as earlier comparators — the union, dedup and depth-max rules never change.
5. **One covering row per (exam × node)** — a unit anchored at several nodes of one exam (Prelims polity + Mains FR) keeps every requirement; the badge set stays the distinct EXAM set (§11 step 5).
6. **Freshness = mapping `effectiveFrom`** (the newest requirement date across coverings); never-attached units sort after dated ones — deterministic and explainable.
7. **The exact §11 step 9 wording is a UI contract**: "Covers: A + B" for shared, "X only" for single-exam (Appendix A) — shipped from the covering-exam set, never inferred client-side from titles.
